# Customer UI assessment — 9 November 2026

Implementation follow-up: the shared customer layout pass and controlled synthetic browser review are recorded in [Customer UI implementation](CUSTOMER-UI-IMPLEMENTATION.md). The assessment below preserves the original findings and distinguishes remaining work from delivered behavior.

Scope: quick source review of the customer route tree, shared navigation/shell, Home, Account, More, Services, connected service workflows and marketplace styles, plus the owner-supplied mobile More screenshot. This is a redesign backlog, not a completed visual audit. No authenticated browser session, full device review, contrast measurement or interaction test was performed. No production data or UI code changed.

## Diagnosis

The shared Bellefort colors, icon family, rounded surfaces and bottom navigation provide a useful foundation. Page structure and interaction patterns still differ. More uses tall destination tiles; several resident services render the general feature-management interface; larger forms use modals; customer and synthetic preview routes can use different implementations. Shared tokens alone cannot resolve these differences.

The supplied More screenshot shows the category strip extending beyond the viewport with a visible horizontal scrollbar. The two-column destination cards spend substantial height on short descriptions. The account-inspection banner is an administrative overlay, not part of ordinary resident navigation, and consumes substantial mobile height. Keep its read-only identity and exit action explicit while making secondary details expandable.

## Shared layout decisions

1. Mobile shell: compact brand header on tab roots; clear back action and page title on detail/task screens. Preserve five labeled bottom destinations: Home, Account, Livelihood, Services, More. Keep adequate content clearance and safe-area padding. For long task forms, prioritize Back/Cancel and one submit action; reserve space for any persistent action above device/keyboard insets.
2. Browse layout: announcements, marketplace, documents and events. Content first, concise search/filter controls, meaningful thumbnails where available. Use imagery for content, not for every utility destination. Keep text-only fallbacks.
3. Personal-record layout: payments, passes, requests, vehicles and permits. Compact rows with title, relevant date, status text and one clear detail action. Detail screens show a concise summary, progress and permitted next actions; secondary references/history can remain expandable.
4. Task layout: booking, request creation, pass creation and listing creation. Prefer dedicated routes/full-page mobile views for long forms. Small sheets are suitable for a short choice, filter or confirmation. Preserve validation values, focus handling, pending state and server confirmation.
5. Desktop: retain the sidebar; use an intentional content width and useful two-column compositions such as list/detail or booking/calendar-summary. Avoid stretching a phone card to the entire desktop width. Forms need readable line lengths.

## Mobile quality criteria for the implementation pass

- Review 360, 390 and 430 CSS-pixel widths, tablet and desktop, including long content and increased text size. Do not treat one screenshot or synthetic route as coverage of a connected route.
- Use 16px body text, at least 14px secondary text and 48px controls. Keep visible focus, labeled icons and status text alongside color.
- Prevent whole-page horizontal overflow. Intentional category browsing must have a clear usable affordance; avoid nested scrolling for ordinary lists.
- Keep one primary action per task. Add immediate pressed/loading feedback and clear recoverable error states. Prevent duplicate submissions.
- Preserve back navigation and context, including filters and scroll position where practical. Do not let fixed controls cover form fields or final rows.
- Verify loading, empty, error, populated, read-only and unavailable states; assess light/dark appearance and reduced motion.
- Keep actual unavailable data honest and synthetic previews labeled. Financial totals, payment status, approval and ownership remain server-owned.
- The existing PWA manifest specifies standalone display. Installation and browser/device behavior need owner verification; this source setting does not establish offline support or native-app parity. Never show cached sensitive records as newly confirmed data.

## Owner reference: compact grouped More tiles

The owner supplied a mobile Support screen with section labels and short two-column tiles. Adopt its compact horizontal icon/label composition as a candidate for More, using Bellefort colors and the existing outline icons. This replaces the earlier all-row recommendation with a hybrid: compact two-column tiles for short frequent destinations, full-width rows for longer labels and account/settings actions. Wrap to one column at narrow widths or large text sizes; do not truncate essential labels or force equal heights with excess whitespace.

Group destinations by resident purpose, with clear headings. Keep search available without requiring a category carousel. Do not reproduce irrelevant warranty/diagnosis features, decorative imagery or the reference's floating assistant. Add a Discover/content section only when there is useful published content to show. Do not duplicate Home, Account or Livelihood links already visible in the bottom navigation without a specific contextual reason. The More screen should shorten the journey to secondary tasks, not become another feed.

### State ownership recommendation

- Keep server data and permissions in the existing TanStack Query/auth layers; avoid duplicating fetched records in a new global store.
- Put shareable navigation state such as committed search, filters, sort, page and selected tab in route/search parameters where it improves Back and deep-link behavior. Keep live text entry separate from committed search when needed.
- Keep transient selections, sheet visibility and unsaved form values local. Use a reducer or discriminated lifecycle state for complex forms when multiple independent flags become difficult to reason about.
- Keep global state small: session identity, permissions and shared appearance/installation preferences as appropriate. No Redux/Zustand dependency is justified by this quick assessment alone.
- Preserve account-preview isolation and clear relevant caches on identity/session changes. Decide draft retention per task; default to in-memory handling for personal or sensitive input, not blanket localStorage persistence.

Next planning should map each customer route to its shared layout, state matrix, responsive behavior and verification checklist. This assessment adds scope and candidate design decisions; it does not implement them or establish that every listed behavior currently fails.
