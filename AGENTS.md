# Working rules

- This directory is the rebuilt portal checkout of `https://github.com/bfehoait/hoa`. The owner integrated and published the rebuild. Inspect the current branch and working tree instead of assuming `main`; older descriptions of an isolated, uncommitted workspace are historical. Do not access other projects or change hosting/database state without explicit authorization.
- User-authorized reference exception (4 November 2026): a read-only clone of `https://github.com/bfehoait/hoa` is allowed in `reference/upstream-hoa` for static information extraction. Never edit/push its source, execute/import its code, reuse its design/assets, or connect to its backend. Keep raw source ignored and denied by the dev server; derived inventories contain metadata only.
- No commit, push, publication, live database connection, or store submission without explicit authorization.
- Current authorization (updated by the owner, 16 November 2026): any co-developer or coding assistant, including Claude and Codex, may implement, review, fix and validate requested work locally. This includes frontend behavior, UI, shared schemas/logic, local backend source, tests, documentation and preparation of backend migrations/scripts. It is not a standing UI-only restriction. Preserve existing work and stay within the requested task; do not require Codex to approve Claude's edits.
- Routine reversible local edits, targeted lint/type/build checks and relevant local unit/component tests are authorized without repeated confirmation. Local browser/E2E/accessibility checks are also authorized when they use a verified local server, synthetic data and mocked or isolated services with no live backend or external side effects. Inspect their setup first; do not assume a local page is disconnected from production. Choose checks proportionate to the change, fix relevant failures and report unverified behavior. The earlier default ban on automated tests is superseded by this owner authorization. Live SQL and authenticated production checks remain owner-run unless separately authorized. Association policy decisions remain with the owner.
- Never import, execute, or reuse reference application code. Evidence is workflow information only.
- All preview records must stay clearly labelled synthetic. Unknown official values remain unavailable.
- No resident control may set payment status, role, approval, or election tally. Production authority must be server-owned.
- Browser preview mode is not authentication or permission enforcement. Never claim it is.
- Preserve React 19, TypeScript, React Router, TanStack Query, shared zod schemas, plain CSS tokens and CSS Modules. No component kits or Tailwind.
- Mobile first, 16px body text, at least 14px secondary text, 48px controls, keyboard focus, reduced motion and safe-area support.
- Owner UI preference: avoid redundant headings and repeated instructions. When a tab or dialog already names the section, omit a second equivalent heading inside it. Keep necessary state, scope, synthetic labels and action guidance concise.
- Avoid duplicate navigation actions to a section already available in the same visible tab bar (for example, a Change in Role & status link beneath the Role & status tab).
- New records are local sample records until backend confirmation exists. Never label local persistence as an HOA confirmation.
- Review substantive changes, typecheck frontend edits, and update affected vault notes. Report what was actually checked and what remains for owner browser verification. Never treat skipped tests as passing.
- No credentials or real personal information in source, logs, fixtures, tests, or screenshots.
- Account creation is a protected workflow: preserve atomic Auth/member linking, independent server permission checks, idempotent request receipts and explicit member_linked success confirmation. Never silently claim existing members by email. When changing this workflow, run the targeted check `npm.cmd run check:account-integrity` (owner-authorized regression check), regenerate the Edge editor artifact when its sources change, and state whether SQL, BFE redeployment or frontend deployment is required. See docs/ACCOUNT-CONNECTION-INTEGRITY.md.
- Protected workflows may be maintained and repaired locally; "protected" means preserve their invariants and run their required checks, not refuse all edits. Do not weaken server authorization or invent fee/ownership/approval rules to make a test pass. Ask for a missing policy decision when necessary while continuing independent work.
- Read `docs/CO-DEVELOPER-GUIDE.md` for the current handoff and validation workflow. Older dated task handoffs describe their own historical scope; they do not impose a permanent agent-specific or presentation-only limit. These repository instructions do not bypass the assistant's own tool permissions, sandbox or platform policies; report an actual tool block accurately rather than treating ordinary local edits as prohibited.
- Execution agreement: respect "assessment only," "wait" and "do not edit yet." Once the owner says "go," "proceed," "do it" or otherwise authorizes implementation, begin the agreed work and carry it through local implementation, necessary related fixes, review and validation. Do not stop at a plan, ask for the same authorization again or defer completion to another assistant. Resolve routine implementation choices yourself; clarify only missing policy, material scope changes or actions outside the existing authorization. Deployment/live-data boundaries still apply.
- Every implementation handoff must tell the co-developer what changed, checks actually run/results, remaining issues, and exact next steps. Include commands, any new SQL files in order, frontend/BFE deployment requirements (say explicitly when none), and a focused manual test checklist with roles/screens/actions and expected outcomes. Separate locally verified behavior from checks the developer/owner must still perform; do not hand off only a file list or an unsupported "everything works."
